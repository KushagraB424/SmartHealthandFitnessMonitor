1. Introduction and Objectives

Physical inactivity is one of the leading risk factors for modern non-communicable diseases. While commercial fitness bands and smartwatches are popular, they frequently depend on external cloud servers, continuous GPS tracking, and proprietary closed-source algorithms.

The Smart Health and Fitness Monitor is a self-contained, native Android application created as a student mini-project. It operates strictly on-device without cloud services, third-party chart libraries, Room ORM, or background daemon services. It adheres to fundamental native Android engineering practices using Java, XML layouts, SQLite, and the hardware accelerometer.

1.1 Core Objectives

  • Physical Activity Monitoring: Estimate footstep counts from raw 3D accelerometer signals ($x, y, z$) via vector magnitude, low-pass gravity filtering, threshold crossing, and time debouncing.
  • Active Duration Tracking: Track active foreground exercise time without counting idle background periods.
  • User Profile Management: Provide input and range validation for user attributes (Name, Age, Gender, Height, Weight), persisted locally in SharedPreferences.
  • Activity Goal Setting: Enable customizable daily step goals stored in SharedPreferences with real-time percentage indicators.
  • Activity Notifications: Trigger a local Android notification upon goal achievement with Android 13+ runtime permission handling and duplicate alert prevention.
  • Daily Activity Records: Maintain persistent daily records (date, steps, duration, goal flag) in an SQLite database using SQLiteOpenHelper.
  • Android Lifecycle Mastery: Handle and explain Activity lifecycle states (Active, Paused, Stopped, Destroyed) with Logcat telemetry under tag FitnessLifecycle.

2. Application Design & Architecture

The application employs a modular three-activity architecture communicating via standard Android Intents and local storage providers:

  • MainActivity: Primary user interface containing the step counter, active timer, tracking toggle button, daily goal configuration, and navigation controls.
  • ProfileActivity: Dedicated biometric profile form with range and type validation, persisted to SharedPreferences.
  • HistoryActivity: Displays past daily records retrieved from SQLite via a ListView with an automatic empty state.
  • DatabaseHelper: Encapsulates all SQLite database operations (table creation, upsert queries, and sorting).
  • DailyRecord: Plain Old Java Object (POJO) representing daily fitness statistics.
  • HistoryAdapter: Custom ArrayAdapter rendering activity cards in the history list.

5. Implementation Explanation

5.1 Accelerometer Step-Detection Algorithm

The step detection algorithm is implemented in MainActivity.java using Android's Sensor.TYPE_ACCELEROMETER. The algorithm follows four systematic stages:

  1. Euclidean Vector Magnitude: Raw acceleration values ($x, y, z$) are combined into an omnidirectional magnitude:
    magnitude = Math.sqrt(x * x + y * y + z * z);
    This ensures that footsteps are counted regardless of device tilt or pocket orientation.
  2. Low-Pass Gravity Filter: Static gravity ($\approx 9.81\text{ m/s}^2$) is isolated using an exponential moving average:
    smoothedGravity = (0.8f * smoothedGravity) + (0.2f * magnitude);
  3. Dynamic Acceleration Deviation: The dynamic footstrike component is computed by subtracting baseline gravity:
    dynamicAcceleration = magnitude - smoothedGravity;
  4. Threshold Crossing and Time Debouncing: A footstep is logged when dynamic acceleration crosses above $2.5\text{ m/s}^2$ and at least $300\text{ ms}$ have elapsed since the prior step. This debouncing filters out hand tremors and rapid vibration artifacts.

Limitations: The algorithm cannot distinguish between walking and bumpy vehicular motion (e.g., bus or car rides). No GPS stride calibration is performed. The application explicitly displays: “Step counts are estimates and are not medical measurements.”

5.2 Activity Lifecycle Architecture

The application strictly separates tracking states from Android lifecycle callbacks:

  • onResume(): When the activity enters the foreground, the accelerometer listener is registered (if tracking is active) and the duration timer is started.
  • onPause(): When the activity leaves the foreground, the accelerometer is unregistered to eliminate battery drain, the timer stops, and today's stats are committed to SQLite.
  • onSaveInstanceState(): Step totals, active duration, and tracking state are saved into the Bundle, ensuring seamless state recovery across device rotation.
  • onDestroy(): Cleanup routines run. Crucially, persistence does not depend on onDestroy() because Android may kill processes directly under memory pressure.

7. Conclusion & Future Scope
